## Gotchas

- **WebGPU needs a secure origin.** Open the game through `http://localhost` or `https`. Opening `index.html` from disk fails, and the game shows its "Cannot start" screen.
- **No `strip = true` in `core/Cargo.toml`.** On this machine's Rust toolchain, `rust-objcopy` cannot find `libLLVM.dylib`, so stripping fails during the build. The release profile leaves it out; the wasm is 69 KB without it.
- **The built wasm is committed.** After changing anything in `core/`, run `./build.sh` and commit `wasm/jadereaper_core.wasm` with the source change, or the browser keeps running the old core. The `Core` workflow rebuilds it and fails when the bytes differ, even after a change that only moves lines, because panic messages carry line numbers.
- **The Rust version is pinned** in `rust-toolchain.toml`, so the wasm built locally matches the one CI builds. To move to a newer Rust, change the version there, run `./build.sh` and commit the new wasm in the same change.
- **Bundled fonts only hold the characters the game shows.** After adding or changing Chinese text in `src/` or `index.html`, run `tools/subset-fonts.sh` and commit `assets/fonts/`. Otherwise the font check in CI fails, and new characters fall back to a system font in the middle of a line.
- **The numbers font is picked by character.** `JR Numerals` in `style.css` applies Caveat Brush to digits and `+ % : , . ×` through `unicode-range`, which must match `NUMERALS` in `tools/fonts.mjs`. Caveat Brush has no `→`, so arrows use the text font.
- **The Pages site only holds listed paths.** `.github/workflows/pages.yml` copies `index.html`, `style.css`, `src/`, `wasm/` and `assets/`. A new top-level file or folder the game loads must be added to its copy step, or it works locally and 404s on the published site. `PUBLISHED` in `tools/serve.mjs` must list the same paths, so `npm start` and the smoke test 404 on a file the deploy would miss. A Pages site is served from a subpath named after the repository, so keep every path the game loads relative.
- **Ids are generated, not hand-written.** Part, upgrade and event ids, upgrade max levels, the martial art, element and reaction tables, state buffer indices and the ink colour live in `content/game.toml`. `tools/gen` writes them to `core/src/generated.rs`, `src/generated.js` and the marked block at the top of `src/shader.wgsl`; `./build.sh` runs it first. Never edit those outputs by hand, and commit them with the content file, because the Pages deploy builds nothing. `cargo test` fails if they are stale or if the content has a duplicate or undefined id. The generator is its own crate so it still runs when the core does not compile yet.
- **The simulation moves in fixed steps.** `jr_update(dt)` only collects real time; the core advances in whole steps of 1/60 s (`TICK` in `core/src/game.rs`), so a run depends on the seed and the inputs, not the frame rate. Code inside `Game::step` may assume `dt` is always `TICK`.
- **No standard float functions in the core.** `sin`, `cos`, `exp`, `powf` and `atan2` give different last bits natively and in wasm, which makes the same run diverge. Use `core/src/fmath.rs` instead (`sqrt`, `floor`, `abs`, `min`, `max` and plain arithmetic are safe). `npm run determinism` plays the same scripted run on both and fails if the state hashes differ; CI runs it.
- **A headless screenshot shows a blank canvas.** The WebGPU canvas of headless Chromium is never presented, so `page.screenshot()` shows the HTML UI over nothing. `tools/play.mjs` makes the page draw into a texture of its own and copies that out; use `npm run shot` or `openGame().shot(path)` to see the game view.
- **Wasm memory views go stale.** `src/main.js` rebuilds its `Float32Array` views of wasm memory on every read, because memory growth detaches old views. Keep that pattern when reading new buffers.
- **Balance numbers** in `core/src/defs.rs` (`KINDS`), `core/src/game.rs` (`xp_for`, spawn rate) and the `[[art]]` entries of `content/game.toml` were tuned only against a bot that walks in circles. The `[[element]]` and `[[reaction]]` numbers are a first pick that nothing has tuned. Treat them all as placeholders.
- **A run without element cards must play as it always did.** `whole_run_is_deterministic_and_matches_the_recorded_summary` in `core/src/game_tests.rs` plays a run with the `element_cards` tune at 0 and compares it with a summary recorded before the martial arts became data. A change to `arts.rs`, to `Game::strike` with no element, or to the level-up offer that moves that summary has changed the base game; an offer must not draw from the random generator for element cards when their chance is 0.
- **Damage from an element or a reaction is plain.** `Game::strike` is for a hit a martial art lands; everything an effect or a reaction does afterwards goes through `hurt_enemy`, which leaves no tag. Calling `strike` from inside an effect would let reactions set each other off without end.
- **Element ids start at 1.** 0 means no element, so the tables indexed by element id (`ELEMENTS`, the tag arrays on an enemy) have an unused entry 0, and in JavaScript element `id` is `ELEMENTS[id - 1]`.
